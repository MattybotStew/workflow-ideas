Internal process playbook

When the template picks the design

The starter theme is imported first, and it decides how the site looks. The sitemap and the wireframes are then built in code to map it, the design is brought up to the content, and the build inherits the constraints. Five phases, taught from a fifteen-page non-profit rebuild.

Theme & starter  ·  Sitemap in code  ·  Wireframes in code  ·  Design  ·  Hand off

Open (45s). This is the sibling of the code-first deck. Same agency, same wireframes-in-code instinct — but the design authority sits with a template we do not own.

Land the inversion early: on a bespoke build you own the design system, so an idea is just work. Here you rent one.

The premise

The template is the design system. You don't own it.

One starter, imported once onto a clean staging site, and every page is a copy-and-reskin of a layout that already exists. The catalogue of possible designs is fixed before the first conversation with the client.

The consequence

Most design ideas on a build like this are answered by the same sentence: "that's not a section the starter has." The process below exists to get that answer early, cheaply, and in agreement — rather than three rounds into design.

Contrast with the bespoke deck: there, "we can't build that" means "that's expensive." Here it means "that's off the table." Different sentence, different process.

If the client is ever going to be unhappy about a missing layout, better they find out in week one than in week six.

Ask first

Every design idea starts with one question: which existing starter section is this? If you can point at one, it's cheap and you build it. If you can't, it needs a decision before anyone draws it.

This is the slide to linger on. Everything else in the deck is a consequence of keeping those three columns in their lanes.

The orange outline is deliberate: the starter is the one holding authority. The wire looks like the thing you're building, but it isn't holding design decisions.

It is a pipeline

Not a loop. Theme → sitemap → wireframes → design → handoff. Each phase narrows the next, and none of them goes backwards to reconsider design authority.

Call it a pipeline out loud. The instinct from the bespoke deck is to loop design and review repeatedly — here the loop happens inside phases 3 and 4, not across the whole process.

Phase 05 sits in a later grid cell deliberately, to read as the exit rather than a peer step.

The canvas row is real, not a diagram I invented — it's how the design file for the worked example is actually organised. Naming the warning sign and the tick is the useful bit: the naming convention is the process stating its own priorities.

Phase 01 — Theme and starter

Import before you draw.

  • One starter, one import, onto a clean staging site. Never onto a site that already has pages.
  • Choose on what's in the box, not on how the demo looks. Count the layouts against the page inventory before you commit.
  • The starter constrains every later decision, so choose it before the sitemap — not after the structure is agreed.
  • Don't mix starters. A second import is how projects get quietly stuck.
  • Decline the plugins the starter bundles unless the client is genuinely taking payments or bookings on site.

Why 04 won

  • Ships six page layouts
  • Enough to duplicate across fifteen pages
  • No new templates needed
The test

Could the page inventory be covered by duplicating what already ships? If not, it's the wrong starter — keep looking.

The sequencing claim is the important one: starter before sitemap. The reverse order is how you end up with fifteen pages and a template that can only express eight of them.

Counting layouts against the inventory is cheap. Redoing the sitemap around a template constraint is not.

Phase 02 — Sitemap

The sitemap is a page, and it is the argument.

  • Write the sitemap before the wireframes. Page-versus-section is the decision that costs most to reverse.
  • Build it as a real page in the prototype, not a diagram. Then it is reviewable, linkable and testable by the client.
  • Give the parent page real children, so breadcrumbs mean something: Home › Programs › Health & Well Being.
  • Mark what is a page and what is a section. Promoting a section later changes navigation, breadcrumbs and URLs.
  • Mark the utility pages that don't count against the contract, and the stakeholder artefacts that never ship.

Why in code

  • Reviewable in a browser
  • Links actually resolve
  • Cheap to reorganise
Reorganisation tax

Moving a page in code is a one-line edit. Moving a box in a diagram means every downstream box, arrow and label moves too.

The parent/child detail is not pedantry. Flat pages give you no breadcrumbs, and breadcrumbs are the cheapest navigation a fifteen-page site can have.

Have the page-count cap visible while this is discussed, not in a contract appendix.

Three marks carry all the weight: parent, scope cut, merged. Each one exists because leaving it ambiguous costs a conversation later.

The scope cut is agreed now, while it costs nothing. It only works as a lever if it was named before there was any pressure to use it.

Phase 02 — the lock

Lock what's expensive to change.

  • Slugs — old URLs may already be in circulation
  • Page count — the contract cap, and what counts toward it
  • Nav items — and what lives inside a dropdown
  • Page versus section, for everything on the list
  • CTA destinations — every button, and where it lands
  • Parent/child structure — drives every breadcrumb
  • The scope cut — named before there's pressure
  • Utility pages — which are free, which count
  • Stakeholder artefacts — which never ship
  • What the build may not add — written down, not implied

Free-tier change versus expensive change. Everything on this list is cheap to decide in week one and expensive to change in week eight, because it propagates.

The last item is the unusual one. Telling the build what it can't do is worth more than telling it what to do.

Phase 03 — Wireframes

Build the wire in code, from the starter's own sections.

  • Wire every page in plain HTML — no framework, no build step, no component library.
  • Assemble each page from the sections the starter actually ships, in the starter's own order.
  • The wire settles content, order and hierarchy. It is not a design and shouldn't look like one.
  • Because it's code, a copy change is a one-line edit — not a frame rebuild.
  • If a layout doesn't exist in the starter, drop it. Don't add custom CSS to chase the prototype.

Two things it must never do

  • Look finished. If it looks designed, reviewers critique the styling instead of the structure.
  • Become the deliverable. Plain HTML, deliberately: nothing here is worth porting.
No framework is a choice

A framework makes the wire look like a product, invites "can we just ship this?", and creates components nobody will maintain. Boring on purpose.

"Looks greyed out" is a feature. The moment the wire looks polished, the client's feedback becomes about colour and spacing, and you lose the structure round.

Plain HTML is the enforcement mechanism for "this is not the product" — there is no port, no framework to unpick, nothing to keep alive after the build.

The one rule that saves the build

The wire is disposable. Say so out loud.

It is never ported, embedded or deployed. When the build starts in the page builder, the wire has already done its job and is thrown away. Say this at kickoff, because the alternative is a build team quietly trying to honour it.

The file says so itself

On a real project, before anyone wrote a rule.

  • Wireframes live on a canvas marked ⚠ with a warning sign
  • Design lives on a canvas marked ✅ with a tick
  • The template's own homepage sits in a canvas called Bin, deleted
  • The wires are 1920 wide; the designs are 1440

Why that's a good sign

A convention nobody policed is the team agreeing already.

  • The naming marks the status before a conversation does
  • Binning the template's page shows it was replaced, not reused
  • The width gap is a real handoff failure — see slide 14
Why it matters

The moment the wire looks like a product, it acquires a constituency. A stakeholder will ask why the live site can't just be the wire with real copy in it — and that question costs more to answer than the whole wireframe phase saved.

Say it in the first meeting, in those words. The question is guaranteed to arrive, and having a pre-agreed answer defuses it.

If the answer is ever "yes, ship the wire", the constraint model has already failed and you should know on day one rather than week eight.

Phase 03 — discipline

Placeholders are a scope control.

Deciding in advance which text is real and which is greeked stops a build being held up by copy that was never going to be approved.

Keep real

Structure is being reviewed, so structure is real.

  • Headings, titles, eyebrow labels
  • Slugs, URLs, nav labels
  • Contact data
  • Structured lists — gift methods, levels, timeline years
  • Section order and count

Use placeholder

Prose is not what's being reviewed, so don't review it.

  • Paragraph body and ledes
  • Card blurbs and story excerpts
  • Photography — labelled placeholders
  • Anything a client will "have a look at later"
  • Section summaries and intros
The rule

Don't polish a paragraph you know is placeholder — you'll polish it twice. And don't build a layout that depends on one photograph's crop, or every later asset swap becomes a rebuild.

This table gets pushed back on. Someone will want to write real paragraphs "since we have them". The answer is that unapproved copy is a liability, not a saving.

Make placeholders visually obvious. A placeholder that looks like real copy will eventually be reviewed, approved, and shipped by accident.

Phase 04 — Design

The design follows the content.

  • The wires settle what the pages say. The design file is then brought up to that content, so it describes the agreed site rather than an earlier idea of it.
  • Design work happens against real structure — real sections, real order, real URLs — not placeholders.
  • Mark the wireframe canvas as provisional, because it is. Anyone finding it later should know.
  • Every change note carries the design file's node ID, or the change can't be found again.
  • The client reviews in the design file; the change lands in the wire; the preview updates.
  • Agree the frame width up front. The wires were drawn at 1920 and the designs at 1440, and reconciling that was real work.

Still the starter's job

  • Design aligns content to the template
  • It doesn't redesign the template
  • Drift away from it is the default failure, and it gets corrected
Expect a pull-back

The wire drifted off-template twice and had to be re-anchored. Treat that as normal, not as a failure — and fix the frame width before it costs a round.

The direction matters and it's the opposite of the bespoke deck: here the wires lead and the design file follows.

Node IDs are unglamorous and essential. Design files reassign them when frames move, so the ID has to travel with the change note or the note is worthless.

The width mismatch is a nice detail to volunteer — 1920 wires against 1440 designs means the two artefacts were never really the same viewport, which quietly invalidates a lot of "it matches" feedback.

Phase 04 — the ladder

Decide the tier before the round starts.

Change freelyWireframe decisions. Cost nothing.
  • Section order within a page
  • Headings and button labels that keep their destination
  • Paragraph length and placeholder tone
  • Which image placeholder goes where
  • Flipping a split section left/right
  • Card counts, within what the starter supports
Bring to a callChanges scope, cost or URLs.
  • A new page or a new slug
  • A new nav or dropdown item
  • A new section type the starter lacks
  • A new colour, font or button style
  • A new CTA destination
  • Promoting a section to a page
NeverNot a preference. A rule.
  • A custom child theme
  • A rebuilt header or footer in the builder
  • A new plugin without a concrete need
  • A second starter import
  • Porting the wire to production
Agree it early

A ladder agreed before round one settles most feedback without a meeting. An unagreed one turns every small request into a negotiation about which tier it's in.

The "never" rung is deliberately short and deliberately absolute. Those five lines are where a fixed-theme build quietly becomes an unbounded one.

If a client asks for something on the never rung, the answer is a conversation about the constraint, not a quiet workaround.

Phase 04 — expectations

Expect the homepage to be argued more than once.

  • That is the process working, not failing. An engagement that never revisits the homepage is being under-reviewed.
  • Front-load it. It is the one page every nav entry points at, so it carries the most downstream cost.
  • When it changes, check the whole site — the hero and the primary CTA are often site-wide, not homepage-only.
  • Get sign-off before spending rounds on inner pages. Approval below the homepage rarely holds.

What round one usually is

  • Nav labels
  • Section order
  • Two sections that shouldn't both be there
Budget for it

The homepage was reworked several times on a real build, including being pulled back to match the template. Plan the rounds, don't treat them as failure.

The uncomfortable slide, and the most useful one. Newer designers read repeated homepage rounds as a sign the work was wrong.

It isn't. The homepage is where the client's positioning gets argued, and that argument has to happen somewhere.

Phase 05 — Hand off

What the build team inherits.

Set once, site-wide

In the theme

  • Colours, typography, container width
  • Logo
  • Header and sticky behaviour
  • Above-header announcement bar
  • Footer
  • Menus and the header button
Per page, in the builder

Page canvases

  • Content into imported layouts
  • Duplicated inner pages
  • Page-level sections only
  • No per-page restyling of globals
  • No header or footer in the builder
Native to the platform

The CMS

  • News as posts and a category archive
  • Contact and signup forms
  • Simple utility pages
  • No plugin unless there's a need
  • Events are a page with sections, not a calendar
What actually ships

The handoff is the decisions and the constraints together — not a design file. A build team that inherits the ladder from slide 15 can say no on its own, without a call.

Three columns, three owners. The most common failure is the middle one leaking into the left — a per-page restyle that quietly forks the design system.

Handing over the rules is what makes the constraint survive the people who wrote it.

Phase 05 — the order that matters

One starter, one import, one inner layout reused.

  1. Import the starter onto clean staging
  2. Set the globals once — colour, type, logo, header, footer, menus
  3. Create every page at its locked slug; empty is fine
  4. Home — copy into the imported layout
  5. Duplicate the inner layout for each service page
  6. About, contact, careers
  7. The support and giving cluster
  8. News as posts, plus its archive
  9. Wire the forms to real destinations
  10. Preview against the wires, then hand off
Why this order

Globals before pages, and pages before forms. Set a global after the pages exist and you have fifteen pages to revisit — which is how a single colour change quietly becomes a day of work.

Step 3 is the one people skip. Creating every page at its slug while empty takes minutes and means the nav, menus and breadcrumbs can be built once, properly.

Duplicating the inner layout is the step that makes fifteen pages cheap. Resist re-designing the fifth one because it feels repetitive.

Honestly

What the template took.

  • The accent colour took three attempts. Retuning a theme's existing palette is not the same as setting your own.
  • A left-align lost to a generic centred rule. Builder stylesheets win by default; you fight them one line at a time.
  • A child theme got created anyway — for a genuine accessibility need. The rule allowed a narrow exception, and taking it was the right call.
  • A paid addon got installed despite a plan that said skip it. The plan was wrong, not the install.
  • Three documents disagreed. The written rules, the process doc and the design file's own sitemap all drifted — each stale in a different way.
  • The footer stayed dark after a rule that says white-with-a-rule, not a dark bar. The wires and the design both still had it.
None of these are reasons not to use it

They're the reason to write the rules down before the build starts — so the exceptions are decided rather than discovered, and no document can quietly go stale while another is canonical.

Show this one. A process deck that only describes the ideal is marketing; the friction is what makes the method credible.

Each item is a mechanism, not a complaint: template palettes resist retuning, builder CSS wins by default, exceptions get taken, documents drift, and a rule you don't check gets quietly undone.

The footer is the sharpest example. A written rule — white footer, not a dark bar — was ignored by both the wireframes and the design, because nothing re-checked the rule against the artefact. Written rules that nobody audits are just good intentions.

What carries to the next build

The template and the wire are replaceable. The process isn't.

Keep

The rules file

One canonical document of slugs, palette, structure and prohibitions. It outranks chat history, and it survives everyone who wrote it.

Keep

The change ladder

Free, call, never. Agreed once before round one, and reused unchanged on every engagement after this one.

Keep

The scope cut

Named before there's any pressure to use it. Then trimming late is a decision rather than a crisis.

The test

This process works on a bespoke code build, on a page builder, and on whatever replaces both. The starter changes; the ladder, the rules file and the pre-agreed cut do not.

Close on the transfer, not the tool. The sibling deck makes the same argument from the other direction — different build target, same discipline.

Close on the "test" line: name the next build target and ask what survives. If the answer is more than these three, the process has been re-invented instead of reused.
